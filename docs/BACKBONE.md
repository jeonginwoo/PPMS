# 뼈대 (BACKBONE) — 확정 스펙이 아니라 출발 스케치

> **한 페이지를 넘기지 않는다.** 단위별 확정은 `docs/features/<NN-slug>.md`에 쓴다.
> 이 문서를 고치는 변경은 반드시 `PROGRESS.md` 결정 기록을 남긴다.
> 여기 적힌 것은 "이렇게 갈 것 같다"이고, **프로토타입이 확인해 주기 전까지는 근거가 없다.**

## 1. 세 영역

| 영역 | 다루는 구간 | 대표 화면 |
|------|-------------|-----------|
| 영업 | 수주 이전 — 제안·견적·계약 진행 | 영업 프로젝트 목록 · 상세 |
| 솔루션 | 수주 이후 — 구축 수행 | 솔루션 프로젝트 목록 · 상세 |
| 유지보수 | 납품 이후 — 계약·사이트·이슈 | 유지보수 계약 목록 · 상세 |

## 2. 프로젝트 테이블 구성 (ERD 방향)

공통 컬럼 테이블 하나 + 영역별 테이블.

```
project (공통)
  ├── sales_project        영업 전용 컬럼
  ├── solution_project     솔루션 전용 컬럼
  └── maintenance_*        유지보수 전용 (계약/사이트 구조는 단위 기획에서 확정)
```

- `project` — 모든 영역이 공유하는 것만: 식별·고객사·프로젝트명·담당자·기간
- 영역별 테이블 — 그 영역에서만 의미 있는 컬럼
  (예: 영업 = 예상 수주액·제안 단계 / 솔루션 = 계약 M/M·진척률)
- 한 프로젝트는 `project` 행 하나를 평생 유지하고, 이관되면 다음 영역의 행이 생긴다.
  이전 영역의 행은 지우지 않는다 — 그것이 이력이다.

## 3. 이관 파이프라인 (이 프로젝트의 줄기)

```
영업 ──수주──▶ 솔루션 ──납품·검수──▶ 유지보수
```

- 이관은 **명시적 행위**다. 상태값을 바꿨다고 자동으로 넘어가지 않는다.
  (v3 교훈: 자동 전이는 권한 경로를 우회한다)
- **역방향 이관 금지.** 되돌림이 필요하면 별도 단위로 기획한다.
- 이관 시점에 다음 영역의 행이 생기고, 이전 영역의 데이터는 보존된다.
- 가동률·알람·권한·감사 같은 기능은 **이 줄기에 붙이는 것**이다.
  줄기가 서기 전에는 만들지 않는다.

## 4. 미확정 — 프로토타입으로 확인할 것

> 확인될 때마다 해당 줄을 지우고, 그 결정을 `PROGRESS.md` 결정 기록과
> 단위 스펙으로 옮긴다. 이 목록이 비면 뼈대가 선 것이다.

- [ ] 공통 `project` : 영역별 테이블은 1:1인가, 1:N(이력)인가
- [ ] 현재 영역(phase)은 공통 테이블의 컬럼인가, 영역별 행의 존재에서 파생하는가
- [ ] 영역 안의 세부 상태(계약대기·진행중·완료 …)는 공통인가 영역별인가
- [ ] 유지보수의 원천은 "프로젝트"인가 "계약"인가 — v3는 계약으로 봤다
- [ ] 영업 단계에서 고객사·프로젝트명이 아직 확정되지 않았을 때의 표현
- [ ] 이관 시 누가 무엇을 확인해야 넘어가는가 (권한 · 필수값 · 되돌릴 수 없음 경고)
- [ ] 세 영역을 한 화면에서 보는 장면이 있는가, 아니면 화면이 영역마다 갈리는가
