# ROADMAP — 기능 단위 백로그

> **순서를 건너뛰지 않는다.** 뼈대(B)가 선 다음에 기능(F)을 붙인다.
> 한 단위 = 프로토 → 스펙 → 구현. **표의 칸 하나가 한 사이클**이고, 한 사이클에
> 두 칸을 채우지 않는다.
> 진행 중 발견한 일감은 이 문서 맨 아래 "발견한 일감"에 **추가만** 한다 —
> 사이클 안에서 몰래 하지 않는다(v3에서 사이클이 비대해진 경로).

표기: `-` 미착수 · `~` 진행중 · `v` 완료

## 뼈대 (B) — 이 순서를 바꾸지 않는다

| # | 단위 | 프로토 | 스펙 | 구현 | 이 단위가 답해야 하는 것 |
|---|------|:---:|:---:|:---:|--------------------------|
| B0 | **뼈대 통합 프로토타입** (B1~B5 + F6 + F8 + F10 + F11) | v | — | — | 스냅샷 `001-b0-backbone` · `002-b0-todo-report`. 스펙 없는 단위 — 여기서 나온 결정이 아래 행들의 입력이다 |
| B1 | 세 영역 골격 · 공통/영역별 테이블 구조 | B0 | - | - | 확정: 1:1 · 이관해도 남김 · phase는 파생 → 스펙으로 옮길 것 |
| B2 | 영업 프로젝트 (목록 · 등록 · 상세) | B0 | - | - | 고객사·프로젝트명 미확정 시 표현 · "진행 중만" 필터 |
| B3 | 솔루션 프로젝트 (목록 · 상세) | B0 | - | - | 자체 생성 허용 여부 · 이관된 건 수정 경로 |

B5까지 끝나면 이 제품의 줄기가 선다. 그 전에는 아래 F를 시작하지 않는다.
**B0은 프로토타입 전용 단위다** — 한 프로토타입이 여러 단위를 덮되, 스펙과 구현은 단위마다 따로 간다.

F의 순서는 선행만 지키면 사용자가 바꿀 수 있다. B는 바꾸지 않는다.

**F9(MCP)는 다른 F와 동급이다.** 앞당겨 아키텍처에 반영하지 않는다 —
v3는 MCP가 제품이었고, 그래서 PMS가 MCP 모양으로 휘었다(호스트 앱 분리 ·
도구 카탈로그 · 2인 트랙 분리). v4는 단일 트랙이다.

## 발견한 일감 (사이클 중 발견 → 여기로만)

- **프로젝트 기록 페이지** (2026-09-19 · B0 프로토타입 리뷰 중 사용자 제안 — 지금은 만들지 않음)
  - 무엇: 프로젝트 상세에서 **진행하면서 발생한 내용을 기록하는 페이지를 생성**하는 기능.
    회의록·결정·이슈 경위처럼 사람이 직접 쓰는 문서.
  - 왜 별도 단위인가: 이슈(F6)와 다르다. 이슈는 **처리해야 할 건**(상태·담당자·완료)이고
    이 페이지는 **남겨 두는 기록**이다. 감사 로그(F7)와도 다르다 — 감사는 시스템이 자동으로
    남기고 이건 사람이 직접 쓴다. 셋을 한 단위로 묶으면 v3처럼 경계가 뭉개진다.
  - 착수 전에 답해야 할 것:
    - 페이지가 붙는 곳이 **공통 `project`인가 영역별 행인가.** 공통에 붙이면 이관해도
      따라가고, 영역별에 붙이면 그 구간의 기록으로 갇힌다 (B0에서 정한 1:1 구조와 직결)
    - 이관된 프로젝트의 페이지를 **누가 계속 쓸 수 있는가** (영업이 쓴 기록을 솔루션이 고치는가)
    - 수정·삭제를 허용하는가, 아니면 append-only인가 (F6 이슈 삭제 논의와 같은 축)
  - 선행: B1(공통/영역별 구조 확정). F6·F7과 경계를 같이 그려야 한다.

- **주간보고 "프로젝트" 칸의 모집단** (2026-09-23 · 업무보고 프로토타입 리뷰 중 사용자 질문 — **결정 보류**)

    "현재 진행중인 담당 프로젝트가 표시되는 건가"였고, **지금 구현은 그렇지 않다.**
