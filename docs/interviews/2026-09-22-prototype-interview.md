# 프로토타입 인터뷰 질문지

2026-09-22

- 대상: 영업, 솔루션 PM·개발, 유지보수(CS) 담당자. 시스템을 직접 사용할 의사결정자도 포함한다.
- 확인할 화면: v4 프로토타입 (`prototype/index.html`)
- 소요 시간: 10분 / 20분 / 30분
- 질문 앞의 `[10]`, `[20]`, `[30]`은 인터뷰 시간에 따른 구분이다. 담당 업무에 맞는 질문을 골라 사용한다.

## 0. 인터뷰 배경과 진행 방법

### 인터뷰 목적

기존에 만든 PMS(v3, `pms_mcp`)에는 프로젝트, 인력 배정, 가동률, 유지보수, 권한, 알림 등 여러 기능이 들어가 있다. 개발 후 피드백을 받으면서, 사용하기 번거로운 기능은 없는지, 정해둔 처리 방식이 실제 업무와 맞는지 현업 인터뷰를 통해 다시 확인할 필요가 생겼다.

이를 위해 v4(PPMS)는 영업 → 솔루션 → 유지보수로 이어지는 기본 흐름만 먼저 프로토타입으로 구성했다. 이번 인터뷰에서는 현재 업무와 화면을 함께 살펴보며 다음 내용을 확인한다.

1. 기존에 만든 기능 중 계속 필요한 것과 줄이거나 빼도 되는 것은 무엇인지
2. 업무를 등록하고 진행한 뒤 다음 부서로 넘기는 과정이 실제 처리 방식과 맞는지
3. 기본 기능만으로 업무를 처리할 때 부족한 부분은 무엇이며, 무엇부터 추가해야 하는지

기존 코드와 PRD는 질문을 준비하는 참고자료로 사용한다. 기존에 구현돼 있다는 이유만으로 v4에도 필요한 기능이라고 보지는 않는다. 실제로 사용하는 상황과 관리 부담을 듣고 반영 여부를 정한다.

### 처음 준비한 질문

아래 세 가지가 직접 준비한 질문이다. 본문에서는 이 질문을 바탕으로 업무별 세부 질문을 정리했다.

| 직접 준비한 질문 | 인터뷰에서 물어볼 내용 | 본문 위치 |
|---|---|---|
| ① 영업, 솔루션, 유지보수 프로젝트 테이블 컬럼 정의 | 각 업무에서 어떤 정보를 입력하고 관리해야 하나요? 목록에서 바로 확인해야 하는 항목은 무엇인가요? | 4. 관리 항목 확인 |
| ② 있으면 좋겠는 기능? 예: 영업 프로젝트 관리용 캘린더 | 현재 업무를 하면서 이런 기능이 있으면 좋겠다고 생각한 것이 있나요? 어떤 상황에서 필요한가요? | 6. 기존 기능의 필요성과 추가 요구 |
| ③ 각 단계별 이관 방식을 어떻게 하면 좋을지? 예: 영업 → 솔루션, 솔루션 → 유지보수 | 각 단계에서 언제, 누가, 어떤 정보를 넘기는 게 좋을까요? 받는 쪽의 확인도 필요한가요? | 5. 부서 간 이관 절차 |

기존 기능의 입력 부담이나 처리 방식에 관한 질문은 코드와 PRD를 검토하면서 보완한 내용이다. 아래 ‘기존 코드와 PRD를 보고 보완한 질문’에 그 근거를 따로 정리했다.

### 기존 피드백 반영

| 피드백 | 이번 인터뷰에서 확인할 내용 |
|---|---|
| 영업과 다른 부서의 의견을 듣고 업무 관리 방식을 정리할 필요가 있음 | 개선하고 싶은 점(7-B), 추가 인터뷰가 필요한 부서(7-C) |
| 조직 개편 시 팀즈의 인원 데이터를 가져오고 정기적으로 갱신할 필요가 있음 | 현재 조직도와 인원 명단을 어디서 관리하는지 확인(6-D5). 연동 방법은 IT·인프라 담당자와 별도 논의 |
| 팀즈 일정 API 연동 가능 여부를 확인해야 함 | 현재 일정 관리 방식과 중복 입력 여부 확인(6-E1). API 지원 여부는 관련 담당자와 별도 논의 |
| 진행률은 지금처럼 담당자가 판단해서 입력하는 방식으로 유지 | 진행률을 입력하는 기준(4-C1)과 유지보수로 이관하는 기준(5-B1)을 함께 확인 |

팀즈 연동은 이번 인터뷰에서 업무상 필요한 부분까지만 확인한다. 데이터를 가져오는 방법이나 갱신 주기 등 기술적인 내용은 별도로 협의한다. AI 챗과 MCP는 이번 인터뷰 범위에 포함하지 않는다.

### 업무 흐름을 확인할 때

최근 진행한 업무 한 건을 떠올리며 등록부터 종료 또는 이관까지 설명해 달라고 요청한다. 일반적인 순서와 다른 사례가 있으면, 화면에서 어떤 부분을 처리하기 어려운지 함께 확인한다.

예를 들어 v3는 ‘프로젝트 완료’와 ‘유지보수 이관’을 각각 처리하지만, 현재 v4는 유지보수로 이관하면서 솔루션 프로젝트를 완료한다. 유지보수로 넘기지 않고 종료하는 프로젝트나, 완료 후 이관을 기다리는 기간이 있는지 확인해야 한다.

현재 프로토타입은 진행률이 100%일 때 유지보수 이관 버튼을 표시한다. 진행률을 100%로 바꾸는 것만으로 완료 처리되지는 않고, 이관을 실행하면 완료로 바뀐다.

진행률을 담당자가 판단해 입력한다면, 100%가 실제 이관 가능한 시점과 일치하는지 확인해야 한다. 검수 완료, 납품일, 유지보수 계약 시작일 중 어떤 기준을 쓰는지 5-B1에서 자세히 묻는다.

### 기존 코드와 PRD를 보고 보완한 질문

아래는 구현 내용을 확인해 질문에 반영한 부분이다. 기능을 유지하거나 제외할지는 인터뷰 후 판단한다.

| 확인한 내용 | 인터뷰에서 확인할 점 | 질문 |
|---|---|---|
| v3는 프로젝트 생성 시 PM 1명을 필수로 지정한다. PRD에는 영업 단계의 PM 필수 조건을 바꾸는 일이 미해결로 남아 있다. | PM이 정해지기 전에도 등록해야 하는지, 그때 누가 관리하는지 | 6-A4 |
| v3는 완료와 이관을 별도로 처리하고, v4는 유지보수로 이관할 때 완료된다. | 완료 후 이관 대기 기간이나 이관 없이 종료되는 경우가 있는지 | 5-B2, 5-B6, 6-A1 |
| v3는 완료한 프로젝트를 재개하면 진행률을 90%로 바꾼다. | 재개한 업무의 진행률을 어떻게 정하는 것이 맞는지 | 6-A2 |
| v3에는 PM이 프로젝트별로 역할의 수정 권한을 조정하는 기능이 있다. | 프로젝트마다 다르게 설정할 일이 있는지, 공통 기준이면 충분한지 | 6-A6 |
| v3에서는 이슈가 ‘고객 확인 대기’에 들어가면 바로 ‘처리 중’으로 되돌릴 수 없다. ‘접수’에서 ‘완료’로 바로 변경하는 것도 막혀 있다. | 고객이 재처리를 요청하거나 간단한 문의가 바로 끝나는 경우를 어떻게 처리해야 하는지 | 6-C1, 6-C2 |

### 진행 시 참고할 점

1. 먼저 현재 업무 방식을 묻고, 그다음 v4 화면을 보여준다. v3 화면은 보여주지 않고, 기존 기능은 6번에서 필요한 항목만 말로 설명한다. v3를 사용해 보지 않은 참여자에게는 현재 엑셀이나 기존 도구로 처리하는 업무를 기준으로 답변을 받는다.
2. 기능 목록을 먼저 제시하기보다, 현재 어떤 일을 어떻게 처리하는지 듣는다. 사용 중인 엑셀이나 보고서가 있다면 공유 가능한 양식도 요청한다.
3. 일반적인 처리 방식과 함께 예외가 있었던 사례도 묻는다.
4. 업무량이나 빈도는 가능하면 월 몇 건, 전체의 어느 정도인지 구체적으로 확인한다.
5. 답변을 들은 뒤에는 이해한 내용을 짧게 정리해 맞는지 확인한다.
6. 불필요하거나 번거로워 보인다는 의견도 이유와 함께 기록한다. 필요한 기능이라도 누가 입력하고 갱신할 수 있는지, 기존 업무와 중복되지는 않는지 확인한다.

## 3. 프로토타입 확인

참여자가 직접 화면을 눌러보도록 안내한다. 사용 방법은 필요한 만큼 설명하고, 찾기 어렵거나 이해가 안 되는 부분을 확인한다.

- `[10]` **S1. 목록 화면** — 여기서 가장 먼저 확인하고 싶은 정보는 무엇인가요? 추가로 보여야 할 항목이 있나요?

- `[10]` **S2. 이관** — 최근 진행한 업무 한 건을 기준으로 이관해 보시겠어요? 실제 절차와 다른 부분이나, 지금 화면에서는 처리하기 어려운 경우가 있나요?

- `[20]` **S3. 상세 화면** — 어떤 업무를 할 때 이 화면을 열게 될 것 같으세요? 확인만 하는 경우가 많을까요, 내용을 수정하는 경우가 많을까요? 하루에 어느 정도 사용하실 것 같나요?

- `[20]` **S4. 불필요한 항목** — 화면에서 굳이 없어도 되겠다고 느끼신 정보나 기능이 있나요?

- `[20]` **S5. 진행률 입력** — 이 방식으로 진행률을 입력하면 업무 중에 사용하기 괜찮을까요? 얼마나 자주 수정하게 될 것 같으세요?

- `[30]` **S6. 계약별 사이트 목록** — 한 계약에 사이트가 45개 정도 있다면, 이 화면에서 필요한 사이트를 찾고 관리하기 괜찮을까요?

- `[30]` **S7. 이슈 관리** — 현재 이슈는 어디에 기록하고 계세요? 이 화면에서 관리한다면 편리하거나 불편할 것 같은 점이 있나요?

- `[30]` **S8. 홈 화면** — 업무를 시작할 때 이 화면에서 확인하고 싶은 정보가 있나요? 자주 열어볼 필요가 없을 것 같다면 그 이유도 말씀해 주세요.

## 4. 관리 항목 확인

### 4-A. 공통

- `[20]` **A1.** 계약하는 회사와 실제 사용하는 고객사가 다른 경우가 얼마나 있나요? 프로젝트를 찾을 때는 어느 쪽 이름으로 검색하시나요?

  프로토타입에는 고객사가 ‘코오롱베니트’이고 프로젝트명이 ‘한국거래소 차세대 상장공시시스템 구축’인 예시가 있다. 현재 고객사 입력란은 하나이므로, 계약사와 최종 고객사를 구분해서 관리해야 하는지 확인한다.

- `[20]` **A2.** 프로젝트를 구분하거나 찾을 때 주로 어떤 이름이나 번호를 사용하세요? 별도로 사내 프로젝트 코드나 계약·회계에서 사용하는 번호가 있나요?

  시스템에서 부여하는 ID 외에 기존 업무에서 쓰는 번호가 필요한지 확인한다.

- `[30]` **A3.** 고객사명은 직접 입력하는 방식과 등록된 목록에서 선택하는 방식 중 어느 쪽이 편할까요?

## 6. 기존 기능의 필요성과 추가 요구

현재 업무 방식과 프로토타입에 대한 의견을 들은 뒤 진행한다. 20분 인터뷰에서는 담당 업무와 관련 있는 항목 1개, 30분 인터뷰에서는 2~3개를 골라 묻는다. 10분 인터뷰에서는 요약 질문 5번으로 필요성과 부담을 확인한다.

아래 질문은 기존 v3 기능과 추가 후보를 바탕으로 정리했다. 기존 기능을 짧게 설명한 뒤 실제로 필요한 상황이 있는지, 사용한다면 어떤 부분이 번거로울지 묻는다. 필요한 기능은 더 간단하게 처리할 방법이 있는지도 함께 듣는다.

추가 요구가 나오면 지금 방식이나 v4 화면에서 어떤 업무가 안 되는지 확인한다. 인터뷰 답변은 유지, 단순화, 제외, 추가 검토로 나누어 정리하되, 모호한 항목은 확인할 질문을 남긴다.

- **A6.** 기존 버전에는 PM이 프로젝트마다 역할별 수정 권한을 정하는 기능이 있어요. 실제로 프로젝트별 권한을 다르게 설정해야 하는 경우가 있나요? 회사 공통 기준으로 정해두면 곤란한 사례가 있을까요?

- **A7.** 누가 언제 어떤 내용을 바꿨는지 확인할 수 있어야 하나요? 변경 이력이 필요한 상황이 있다면 말씀해 주세요.


### 6-C. 유지보수 이슈

주로 CS 담당자에게 질문한다.

- **C1.** 처리가 끝났다고 안내했는데 고객이 아직 해결되지 않았다고 하면 어떻게 처리하시나요? 기존 이슈를 다시 진행 상태로 바꾸나요? 이런 경우가 얼마나 자주 있나요?

  기존 버전에서는 ‘고객 확인 대기 → 처리 중’ 변경이 막혀 있어 완료 후 재개해야 한다. 실제 대응에 필요한 상태 변경인지 확인한다.

- **C2.** 이슈 상태를 ‘접수 → 처리 중 → 고객 확인 대기 → 완료’로 구분하면 실제 업무에 맞을까요? 전화 한 통으로 해결한 문의도 각 단계를 거쳐 기록해야 할까요? 이슈 유형은 장애, 문의, 요청 외에 더 필요한 것이 있나요?

- **C3.** 이슈를 잘못 등록했을 때 내용을 수정하는 기능과 삭제하는 기능이 각각 필요할까요? 등록자와 담당자 중 누구에게 허용하면 좋을까요?

- **C4.** 이슈를 등록하면 해당 사이트의 담당 엔지니어에게 자동 배정되는 방식은 어떠세요? 담당자가 바뀌었을 때 알림도 필요한가요?

- **C5.** 고객이 시스템에 직접 이슈를 등록할 필요도 있나요, 내부 담당자가 접수해서 관리하면 될까요?

  고객이 직접 사용하는 범위까지 필요한지 확인한다.

- **C6.** 이슈 목록의 열 — 지금 목록에는 구분, 제목, 프로젝트(유지보수는 사이트), 상태, 담당자, 접수일이 보입니다. 이 중 목록에서 빼도 되는 항목이 있나요? 반대로 목록에서 바로 보여야 하는데 빠진 항목이 있나요? (예: 긴급도, 처리 기한, 요청한 고객 담당자, 완료일)

  목록에 둘 열과 상세 화면에만 둘 항목을 구분한다.

### 6-D. 알림, 권한, 조직

- **D1.** 어떤 상황에서 알림을 받으면 도움이 될까요? 시스템 안, 메일, 팀즈 중 어디로 받는 게 편하세요? 알림이 너무 많다고 느끼는 기준도 있나요?

  먼저 의견을 듣고, 필요한 경우 배정, 완료, 마감 7일 전, 완료 지연, 이슈 담당자 지정 등을 예로 든다.

- **D2.** 알림 종류별로 받을지 선택할 필요가 있나요? 전체 알림을 켜고 끄는 정도면 충분할까요?

- **D3.** 계약 만료나 프로젝트 마감 전에 알림이 필요한가요? 누구에게, 며칠 전에 알려주면 좋을까요?

- **D4.** 프로젝트나 계약금액을 볼 수 있는 범위를 제한해야 하나요? 팀장과 팀원은 각각 어느 범위까지 조회할 수 있어야 하나요?

  부서별 조회 범위와 금액 등 특정 정보의 공개 범위를 나누어 확인한다.

- **D5.** 조직도와 인원 명단은 현재 어디에서 관리하고 계세요? 조직 개편이 있으면 누가 수정하나요? 이 시스템에서도 직접 관리할 필요가 있나요?

  기존에 관리하는 곳이 있다면 연동 검토 시 참고한다. 가져오는 방법은 별도 논의한다.

- **D6.** 조회 권한이 없는 프로젝트는 목록에서도 보이지 않아야 하나요? 프로젝트가 있다는 것은 알 수 있되 상세 내용만 제한하는 방식이 필요한 경우도 있나요?

### 6-E. 그 밖의 기능

먼저 “현재 업무를 하면서 이런 기능이 있으면 좋겠다고 생각한 것이 있나요? 어떤 일을 할 때 필요한가요?”라고 묻는다. 답변을 들은 뒤 아래 항목 중 관련 있는 것을 골라 구체적으로 확인한다.

- **E1. 일정** — 영업 프로젝트 관리용 캘린더가 있다면 어떤 일정을 확인하고 싶으세요? 고객 미팅, 제안·견적 제출, 착수 예정일 등이 필요한가요? 솔루션과 유지보수 업무에서도 검수일, 계약 만료일, 고객 방문 일정을 함께 볼 필요가 있나요? 지금은 어디에 일정을 등록하고 계세요?

  팀즈 등 기존 일정과 중복해서 입력하게 되는지도 확인한다. 현재 일정 관리 방식은 팀즈 연동 논의 때 함께 전달한다.

- **E2. 엑셀** — 어떤 목록이나 자료를 엑셀로 내려받아야 하나요? 기존 엑셀을 한 번에 업로드하는 기능도 필요한가요?

- **E3. 첨부파일** — 제안서, 견적서, 계약서는 현재 어디에 보관하고 계세요? 시스템에 파일을 직접 올려야 할까요, 공유폴더 링크를 연결하면 될까요?

- **E4. 프로젝트 기록** — 회의록이나 결정 사항을 프로젝트별로 남길 수 있으면 사용하시겠어요? 현재 이런 기록은 어디에 작성하고 계세요?

  처리 상태를 관리하는 이슈 외에, 회의 내용이나 결정 경위를 남길 공간이 필요한지 확인한다.

- **E5. 모바일** — 외근이나 고객사 방문 중 휴대폰으로 확인할 일이 있나요? 조회만 가능하면 될까요, 현장에서 입력하거나 수정할 필요도 있나요?

## 7. 마무리와 우선순위

의사결정자에게는 우선순위(A)와 도입 시점(E)도 확인한다. 짧은 인터뷰에서는 업무별 상세 질문을 줄여 시간을 조정한다.

- `[10]` **A.** 오늘 본 기능 중 꼭 남겨야 할 것은 무엇인가요? 줄이거나 빼도 괜찮은 기능도 있나요? 기본 기능만으로 업무를 처리하기 어렵다면, 가장 먼저 보완해야 할 것은 무엇인가요?

- `[20]` **B.** 업무 관리 방식이 정리되면 어떤 점이 가장 달라졌으면 하세요? 지금 방식 때문에 누락, 중복 작업, 일정 지연 등이 생긴 사례가 있나요?

- `[20]` **C.** 영업, 솔루션, CS 외에 이 시스템을 사용할 부서가 또 있나요? 추가로 의견을 들어보면 좋을 담당자도 알려주세요.

- `[30]` **D.** 기존 데이터를 새 시스템으로 옮겨야 하나요? 진행 중인 건, 최근 몇 년치, 전체 이력 중 어느 범위가 필요한가요?

  참고로 저장소 문서에 기재된 v3 데이터 규모는 인원 44명, 프로젝트 382건, 유지보수 계약 105건이다. 실제 이관 대상과 최신 건수는 별도로 확인한다.

- `[30]` **E.** 언제부터 사용할 수 있어야 하나요? 기존 방식과 함께 사용하는 기간이 필요한가요?

- `[10]` **F.** 오늘 질문에 없었지만 추가로 말씀하고 싶은 내용이 있나요?

## 8. 인터뷰 후 정리

인터뷰한 날 답변과 받은 자료를 정리한다.

1. 기능별로 유지, 단순화, 제외, 추가 검토 의견과 이유를 정리한다. 필요한 이유뿐 아니라 누가 입력하고 관리할 수 있는지도 남긴다. 한 사람의 의견만으로 제외를 확정하지는 않는다.
2. 업무 흐름에서 맞지 않았던 부분을 정리한다. 등록 시 미확정 정보, 완료와 이관 시점, 이관 없는 종료, 상태 되돌리기 등의 사례를 기록하고, 합의된 변경은 `docs/BACKBONE.md`에 반영한다.
3. 미확정 항목 중 합의된 내용은 `docs/PROGRESS.md`의 결정 기록과 해당 기능 문서에 근거를 남긴다. `docs/BACKBONE.md`의 미확정 목록도 함께 갱신한다.
4. 계약 갱신, 견적 이력, 하나의 영업 건에서 여러 프로젝트가 생기는 사례는 따로 모은다. 현재 데이터 구조로 처리할 수 있는지 검토하고, 변경이 확정되면 관련 설계에 반영한다.
5. 새로 나온 기능 요구는 `docs/ROADMAP.md`의 ‘발견한 일감’에 추가한다. 개발 시점과 우선순위는 이후에 정한다.
6. 조직·인원 관리(6-D5)와 일정 관리(6-E1)에 대한 답변은 팀즈 연동 논의에 전달한다.
7. 부서나 담당자마다 의견이 다른 항목은 각 의견과 이유를 남기고, 추가로 합의해야 할 사항으로 구분한다.
8. 받은 엑셀과 보고서 양식은 다음 프로토타입에서 관리 항목과 화면 구성을 검토할 때 참고한다.
