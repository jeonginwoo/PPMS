## 1. 영업

### 1-1. 화면 구조

- **단계별 메뉴 분리.** 리드 · 제안 · 견적 · 수주를 **트리 구조**로 나눠 달라. (3-S1)
- 목록에 **검색과 필터**가 없다. 둘 다 필요. (4-B7)
- 프로젝트명은 어떤 목록에서든 **항상 보여야** 한다. (4-C7)
- **열 개인화** 요청 — 목록에서 볼 열을 사용자가 고를 수 있으면 좋겠다. (4-C7)

### 1-2. 관리 항목

- **고객사와 발주처를 구분**해서 따로 관리한다. (4-A1)
- 한 프로젝트에 **솔루션을 여러 개** 선택할 수 있어야 한다. 계약은 쪼개지 않는다. (4-A4)
- 단계는 **‘계약이 되어야’** 수주로 본다 — 리드·제안·견적·수주 어휘 자체는 문제없음. (4-B2)
- 못 딴 건은 **‘실주’** 상태로 남긴다. (4-B1)
- 금액은 **단순 계약금액 → 총매출** 기준. 부가세·연간 환산·외화는 언급 없음. (4-B3)
- 견적 차수는 **따로 보관하지 않고 로그로** 본다. (4-B4)
- **M/M 등급(초급·중급·고급)을 최초 등록 시점에** 입력한다. (4-B7)

### 1-3. 목록·상세에 더 필요한 것 (4-B7)

- 프로모 노트 + **첨부문서**(견적서 업로드 포함)
- **고객 연락처** — 상세보기에
- **최종 컨택 일시** 자동 갱신
- **진행사항 업데이트 로그**
- **선금 예정일 · 잔금 예정일 · 검수 확인일자**

### 1-4. 솔루션·유지보수에 대한 영업의 의견

- 계약 M/M과 실제 투입 M/M을 **나누지 말고 하나로** 관리. (4-C3)
- 대신 **실제 투입 기간과 개발 기간을 구분**한다. 이 둘은 **영업·솔루션 양쪽에서** 확인. (4-C4)
- 유지보수 계약 갱신 시 금액은 **오르기도 내리기도** 한다. (4-D1)
- 유지보수 계약 기간은 **회사마다 다르지만 대개 1년**. (4-D3)
- 유지보수 계약 목록에 **고객대표**가 필요. (4-D8)

## 2. 솔루션

- 개인적으로 쓰는 방식: **task 단위 · 업무 단위로 요구사항 분석과 설계**를 쪼개 관리한다. (2-D)
- 이슈는 **사이트가 아니라 프로젝트 기준**으로 본다. (3-S7)
- 유지보수 정보도 **사이트명이 아니라 프로젝트명**으로 찾는다.
  → **프로젝트 ID가 난수로 생성되더라도 매핑**이 되어야 한다. (4-D2)

## 3. CS(유지보수)

### 3-1. 이슈 작성 (3-S7)

- 내용이 길어지면 **새 페이지로 이동**해서 작성.
- **코드 형식** 입력을 받을 수 있어야 하고, **이미지가 잘 보이게** 들어가야 한다.
- **이슈 템플릿**을 설정에서 정의 — `문의 내용 → 원인 파악 → 작업 내용`(원인 분석·조치 내역) 틀이 자동으로 로드되면 좋겠다.

### 3-2. 이슈 목록 (3-S7, 6-C6)

- **담당자 기준**으로 내 이슈가 먼저 보이게.
- **필터는 전부** 달아 달라. 값(예: 특정 고객사)을 클릭하면 **바로 그 값으로 필터링**되면 좋겠다.
- **고객 담당자** 열 필요. **긴급도는 애매** — 케이스 바이 케이스라 넣기 곤란하다.
- 완료 처리 시 **완료일을 따로** 기록.
- **완료된 건을 다시 살리는**(재오픈) 동작이 필요하다.
- 진입 경로가 셋이다 — **사이트 → 이슈 목록**, **프로젝트 → 히스토리**, **고객사**.
- 상태는 `접수 → 처리 중 → 고객 확인 대기 → 완료` **현상 유지**. (6-C2) → §5에서 갈린다
- 이슈 등록 시 **담당 엔지니어 자동 배정은 굳이 필요 없다.** (6-C4)
- 추가 희망: **업체 담당자 별점(특이사항)**, **이슈 난이도**.
- **메일 알림**이 오면 좋겠다.

### 3-3. 이관 (인수인계) — CS에서 가장 강한 요구

- **필수 입력 탭을 만들어, 다 못 적으면 이관 처리가 되지 않게** 막아 달라.
- 필수 항목으로 언급된 것: **패키지 버전 · 톰캣 버전 · SSL 여부 · 변경 모듈 · 체크리스트 · 프로젝트 이슈 · 인수인계서 틀**.
- 프로젝트 부서 쪽에서 **이관 대기 / 이관 완료**를 탭으로 분리해 관리.
- **완료 건에서 히스토리**를 볼 수 있어야 하고, **이슈 페이지에서 완료된 프로젝트로 넘어가는 링크**가 필요.

### 3-4. 정기점검 — 신규 요구

- 유지보수 계약 목록에 **정기점검 유무**(월 · 분기 / 원격 · 방문 구분)가 필요. (4-D8)
- **정기점검 탭을 따로** 만들어 달라(원문에서 가장 강조된 항목).
- **정기점검 문서 관리**, **완료 표시**, **일정** 관리.
- **외근 일정**을 캘린더에 표시.

### 3-5. 공통 항목

- 이슈에도 **고객사와 유지보수 계약사 둘 다** 들고 와야 한다. (4-A1)
- 중간중간 **테스트 페이지를 배포해서 확인**하면 좋겠다. (진행 방식 요청)
- 계약 유형으로 **재구축 건 / 추가 개발 건** 구분이 있다.

## 4. 추가 메모 — 대상 미기재

> `PMS 인터뷰.txt` 와 `추가 인터뷰 메모1.txt` 두 파일에는 **대상자가 적혀 있지 않다.**
> 내용이 서로 겹쳐 주제별로 합쳤다. 누구의 발언인지 확인이 필요하다(§6).
> 위 §1~§3과 달리 **부서 귀속을 알 수 없으므로** 여기 둔다.

### 4-1. 영업 · 계약 · 금액

- **가장 중요한 것: 수주 → 수금 → 매출로 이어지는 흐름을 확인하는 것.**
- **프로젝트 생성 시 첨부문서를 함께 등록** — 미(프로모)노트, 견적서.
- **고객 정보(연락처 등)**, **최종 연결 일시 자동 갱신.**
- **검수 확인 일자**, **선금 · 중도금 · 잔금 일정.**
  (원문에 “유지보수 테이블에서 관리?”라는 의문이 함께 적혀 있다 — 어디에 둘지 미정)
- **금액은 변동될 수 있다 → 히스토리로 남긴다.**
- **영업 단계 컬럼을 목록 페이지로 분리**한다(프로젝트의 하위 페이지).
  → §1-1의 “단계를 트리 구조로”와 같은 요구.
- 영업 테이블 컬럼: **고객사 / 계약사(발주처) 구분 · 매출(예상수주액) · 단위(core, copy) · 메모 · 첨부문서.**
- **프로젝트명이 끝까지 보이게** — 2줄로 접히거나 열이 넓어져도 괜찮다.
- **보고 싶은 컬럼만** 볼 수 있도록.
- 최초 등록 시 **초급 · 중급 · 고급 M/M 설정.**

### 4-2. 솔루션 · 태스크 · 진행률

- **솔루션에는 제품명과 수량**이 들어간다.
- **투입 인력 프로필 조회.** 단, **수주가 완료되어야 투입 인력을 지정**할 수 있다.
- 개발 흐름은 **요구사항 → 분석 · 설계 → 개발.**
- **프로젝트별로 개발자가 태스크를 등록**하고, 태스크로 진행률을 맞추는 방식이 좋다.
  다만 **복잡해지고, 프로젝트별 커스텀 영역이 많다**는 것이 함께 적혀 있다.
- 진행률이 **초과하면 경고 표시**(빨강 + 알림).
- **솔루션 이관 시 이슈도 함께 이관**한다.
- 이관 시 **등록 날짜 히스토리**를 남기고, **이관 최종 날짜**를 지정한다.
  그 날짜를 기준으로 계약을 확인할 수 있다.

### 4-3. 유지보수 · 이슈

- 계약은 **신규 / 유지**로 구분한다.
  **유지** = 이미 유상으로 했고 이어서 하는 것. **신규** = 처음 유상으로 들어가는 것.
- **유지보수를 달력으로** — 갱신일 · 마감일이 캘린더에 시각적으로 표시되면 좋겠다.
- 들어오는 이슈는 **프로젝트에 매핑**한다. **등록 날짜 히스토리**를 남긴다.
- **이슈 상태를 세분화**한다. → §5에서 CS 답변과 갈린다.
- **“지금 1:N → 1:1로 수정 예정”** — 무엇의 관계인지 원문에 없다(§6).

### 4-4. 프로젝트의 범위 확장

- 솔루션 프로젝트에 들어가지 않는 건이 있다 — **용역 · 마케팅 · 연구소**, **매출이 없는 프로젝트.**
- **내부 / 외부** 구분, **PoC**.

### 4-5. 회계 (신규 영역)

- **매출액 · 총액 관리.** 매출을 **경영 쪽에서 나중에 관리할 수 있도록 확장.**
- **매출 · 매입 통계** 기능.
- 금액 계산 원리는 **부사장님 인터뷰에서 확인**할 것.

### 4-6. 보기 권한 · 검색 · 문서

- **자기 프로젝트를 먼저** 볼 수 있게. **전체 / 부서별 필터링.**
- **검색 기능**(영업 목록 포함).
- **프로젝트 문서 중앙화** — 검색으로 필터링.
- **이력 관리.**

### 4-7. TODO · 업무보고

- **TODO에 월별 보기 추가.**
- **일일보고는 어려울 수 있다 — 최대한 간편화·접근성 우선.**
- **업무보고 탭도 개인화. 복사해서 사용하는 방식.**
  (`추가 인터뷰 메모1.txt`에는 “**업무보고 탭 보류**, 개인 페이지로 만들어서 복붙”으로 적혀 있다)
- 부서 간 연동은 **task 단위**로 나누고, **TODO에서 task 티켓을 선택**하는 방식.

### 4-8. 공유 · 확장

- **공유 전파가 잘 되도록** 구성. **이슈 공유**가 최대한 잘 되고, **해결되면 알림.**
- **챗봇 연결**이 되면 아주 좋겠다. (→ ROADMAP F9)
- **데이터가 많아질 때를 대비.** 저장은 **DB로 하고, 나중에 OpenSearch를 추가**한다.
- 마인드맵은 왼쪽보다 **오른쪽을 늘리자**.

### 4-9. 우려로 적힌 것

- **“고객사 담당자 개인정보 있으면 편하긴 한데 문제가 될지도.”**
  §1-3·§3-2의 ‘고객 연락처 · 고객 담당자’ 요구와 같은 대상을 가리킨다.
  편의와 개인정보 취급이 맞서는 유일한 항목이므로 따로 남긴다.

## 6. 뜻을 확인해야 하는 말

원문에 그대로 적혀 있으나 의미를 단정할 수 없는 것들. **추측해서 스펙에 넣지 않는다.**

- **“지금 1:N → 1:1로 수정 예정”** (`PMS 인터뷰.txt`) — 무엇과 무엇의 관계인지 없다.
  유지보수 문단 안에 있어 **계약:사이트**로 읽히지만, BACKBONE의 핵심 결정을 뒤집는 문장이라
  추측으로 넘길 수 없다. **§5의 기준 축 합의와 같은 자리에서 확인한다.**
- **“요나”** — CS 원문에 네 번 나온다. 제품/시스템 이름인지, 담당자인지, 이슈 출처 채널인지 불명.
  “요나 처리 완료는 완료로 보이게”라는 표현으로 보아 **외부 시스템의 상태를 가져오는 연동**일 가능성.
- **“브이서치”** — CS 원문에서 느낌표 셋과 함께 강조. 검색 도구 이름(vSearch)으로 추정되나 확인 필요.
- **“프로독아이”** — `추가인터뷰메모_cs.txt`. 문서 관리 도구로 추정.
- **“사이버다임 1.1.3 — 개인정보 내부 6201에서 하는 걸로 변경, 기존은 6501”** —
  특정 고객사의 포트/버전 변경 이력으로 보인다. PMS 요구사항인지 현장 메모인지 불명.
- **“요일?”** (유지보수 문단), **“손해 !??!”**, **“30010 / 31108”** — 문맥 없음.
- **`PMS 인터뷰.txt` · `추가 인터뷰 메모1.txt`의 대상자** — 누구의 발언인지.
